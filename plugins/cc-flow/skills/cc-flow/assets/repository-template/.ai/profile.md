# 研发配置档案

> 只配置两个维度。默认值适合大多数项目，不需要为了使用本流程而改变现有架构。

delivery_level: standard
architecture_style: existing

## 交付级别

### `prototype`

用于探索、验证和短期原型。保持实现简单，至少验证核心路径、构建可用性和明显风险；不得降低安全、隐私、真实测试证据和高风险审批要求。

### `standard`（默认）

用于普通生产项目。要求完整验收、必要回归测试、兼容性分析、错误处理、文档同步和可回滚性。

### `enterprise`

用于高影响或长期运行的生产系统。在 `standard` 基础上，根据任务风险补充：

- 明确的 SLO、容量和性能目标。
- 安全威胁、权限、隐私与审计检查。
- 超时、重试、幂等、降级和故障恢复策略。
- 日志、指标、链路、告警和运行手册。
- 数据迁移、发布、回滚和兼容性验证。
- 外部接口契约及必要的集成、性能或恢复测试。

## 架构风格

### `existing`（默认）

保持项目现有架构，只修复与任务直接相关的边界问题；不借任务之机进行架构迁移。

### `layered`

明确表现层、应用层、业务/领域层和数据/基础设施层职责，禁止绕过层级边界的随意调用。

### `clean`

业务规则和用例保持独立，依赖指向内层；框架、数据库和外部系统作为外层实现。

### `hexagonal`

业务核心通过端口定义能力，外部系统通过适配器接入；核心不得直接依赖具体基础设施。

### `ddd`

仅用于业务规则复杂且领域边界值得长期维护的项目。要求：

- 使用统一语言，识别限界上下文及上下文关系。
- 用实体、值对象、聚合和领域服务表达业务不变量。
- 聚合边界与事务一致性边界一致，跨聚合通过明确协作机制处理。
- 仓储接口服务于领域模型，基础设施提供实现。
- 区分领域事件与集成事件，外部模型通过防腐层隔离。
- 避免按数据表机械创建聚合，也不为简单 CRUD 强行套用 DDD。

## 使用规则

1. 初始化时默认使用 `standard + existing`。
2. AI 可以根据项目证据提出调整建议，但不得自行改变配置。
3. 改变配置必须说明原因、影响和迁移成本；涉及架构迁移时创建独立任务。
4. 配置只提高适用门槛，不会取消 `.ai/conventions.md` 的基础安全、测试、评审和审批要求。
