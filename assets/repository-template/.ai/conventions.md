# AI 软件研发协议

本文件是仓库内 AI 开发行为的主规范。工具入口文件只做引用，不应复制出另一套相互冲突的规则。

## 1. 适用范围

本协议自动适用于：

- 新增、修改或优化软件功能，修复缺陷，重构代码。
- 修改测试、技术配置、数据结构、依赖、构建或部署机制。
- 继续执行已有 CC Flow 任务的 Plan、Implement、Test、Review 或 Document 阶段。
- 初始化、刷新或明确调用 CC Flow。

以下请求默认不进入本协议：

- 只读问答、代码或架构解释、仓库探索、调研和状态查询。
- 报告、总结、资料整理以及不改变软件行为的独立文档生成。
- 不属于已有开发任务的独立只读测试或评审。

对排除项不得创建或更新 `.ai/tasks/`、`.ai/progress.md` 或其他流程证据，也不要求预读全部项目上下文；只读取回答所需的资料。用户明确调用 `$cc-flow` 时视为主动选择本协议。只读请求后来转为软件修改时，必须在修改前进入本协议。

## 2. 指令优先级与冲突

按以下顺序处理：

1. 安全、隐私、法律与平台强制规则。
2. 用户对当前任务的明确要求。
3. 更深目录中更具体的仓库规则。
4. 本文件、`AGENTS.md` 与当前任务文件。
5. 现有代码、测试和文档表达的项目约定。

发现冲突、资料明显过时或任务目标无法同时满足时，不要自行掩盖；应说明冲突和可选方案。

## 3. 开工前必读

开始计划或修改前必须阅读：

- `.ai/workspace.yaml`（存在且适用时）
- `.ai/project.md`
- `.ai/profile.md`
- `.ai/architecture.md`
- `.ai/business.md`
- `.ai/progress.md`
- 当前任务的 `task.md`、`plan.md`
- 任务涉及目录中的局部规则与相关测试

如果这些文件仍有影响当前任务的占位符或相互矛盾，先补齐事实或明确假设。

当 `.ai/workspace.yaml` 存在时，跨仓库需求必须建立协调仓库父任务和受影响仓库子任务。不要把客户端需求默认理解为只改客户端，也不要强制无关仓库参与。各仓库仍独立遵守本仓库计划、测试、评审和审批门槛。

## 4. 配置档案

每个纳入本协议的任务必须遵守 `.ai/profile.md` 中的两个配置：

- `delivery_level`：`prototype / standard / enterprise`
- `architecture_style`：`existing / layered / clean / hexagonal / ddd`

默认使用 `standard + existing`。配置应用原则：

1. `prototype` 可以减少非必要抽象和文档，但不能取消安全、隐私、真实测试证据和高风险审批。
2. `standard` 使用本文件的完整默认完成标准。
3. `enterprise` 根据任务影响增加 SLO、弹性、安全、审计、可观测性、迁移、发布回滚和专项测试证据。
4. `existing` 优先保持现有架构；其他架构风格只约束相关代码，不自动授权全项目重构。
5. `ddd` 只用于复杂业务领域，必须围绕统一语言、限界上下文、聚合不变量和依赖方向，而不是机械增加目录和类型。
6. AI 可以建议调整配置，但未经用户或项目负责人确认不得修改 `.ai/profile.md`。

## 5. 任务分级

### 简单任务

同时满足以下条件才可视为简单任务：

- 通常只改一个文件，或是与软件交付直接相关的局部文档/机械性修改，且不属于上述排除项。
- 不改变公开接口、数据结构、业务规则、权限、安全边界或依赖。
- 可快速验证并容易回退。

简单任务可不创建完整任务目录，但仍需检查影响、验证结果和文档同步。

### 标准任务

符合任一条件即为标准任务：

- 修改两个或更多文件。
- 改变运行行为、接口、数据、配置或测试。
- 修复需要分析根因的缺陷。

标准任务必须先创建任务目录并完成计划。默认在计划完成后取得用户或负责人确认；若任务已明确授权自主执行，可将 `approval` 标记为 `not_required` 并写明依据。

### 高风险任务

涉及生产数据、数据迁移、权限认证、支付、安全、隐私、不可逆操作、基础设施或大范围兼容性变化的任务属于高风险。高风险任务必须人工批准计划与回滚方案；不得用 `not_required` 绕过批准。

## 6. 标准工作流

```text
UNDERSTAND → PLAN → APPROVE → IMPLEMENT → TEST → REVIEW → DOCUMENT → DONE
```

### UNDERSTAND

先从用户描述和仓库证据中明确用户目标、用户场景、成功标准、非目标、现状、约束、依赖和未知项。已有信息足够时直接继续；只有缺失信息会实质改变范围、用户价值、业务行为或成功标准时，才提出最多 1～3 个简短问题。明确 Bug、机械修改或已批准方案不做形式化产品访谈。

用户提出的界面、技术、组件或架构做法必须与真实需求分开：除非用户明确要求或项目证据表明它是强制约束，否则将其视为候选方案，并在 PLAN 中比较可选方案、给出推荐与取舍。关键产品意图未明确前不得创建新任务、制定实现计划或修改代码。

### PLAN

在 `plan.md` 中写明：

- 当前交付级别和架构风格，以及本任务适用的额外门槛
- 用户目标、用户场景、成功标准，以及用户提出方案的属性
- 现状与根因（缺陷任务必填）
- 可选方案、推荐方案与关键取舍
- 预计修改的文件/模块及原因
- 数据、接口、兼容性、安全和运维影响
- 测试计划
- 风险、缓解措施与回滚方案

计划批准前不得开始标准或高风险任务的代码修改。

### 轻量任务拆分与 Subagent

标准和高风险任务在 `plan.md` 中选择一种执行模式：

- `single`：默认模式，由主 Agent 完成。
- `coordinated`：存在多个工作流，但因共享文件、契约或前置依赖而顺序执行。
- `parallel`：至少两个工作流边界清晰、可以独立完成，并行能明显改善速度或质量。

使用原则：

1. 不按文件数量机械拆分，按独立交付结果、依赖关系和写入边界判断。
2. 优先把只读调查、测试、日志分析和独立评审交给 Subagent。
3. 并行修改代码前必须稳定共享接口、数据结构和业务规则，并为每个工作流指定互不重叠的写入范围；出现重叠或新依赖时改为顺序执行。
4. 不为每个 Subagent 创建任务目录。只有跨仓库工作，或确实需要独立验收、审批和生命周期的交付项，才建立持久子任务。
5. 主 Agent 负责批准后的编排、结果汇总、冲突处理、集成验证、任务状态和文档；Subagent 不得自行扩大范围或权限。
6. 工具不支持 Subagent、拆分收益不明显或协调成本更高时，保持 `single`，不把多 Agent 当作完成条件。

### IMPLEMENT

- 只修改计划范围内的内容；范围变化先更新计划。
- 遵循现有架构和代码风格，优先最小、完整的变更。
- 不无理由重构无关代码，不覆盖或清理他人的无关改动。
- 不删除兼容逻辑、不改变公开行为，除非任务明确要求且计划已说明。
- 引入新依赖前说明必要性、许可证/安全风险和替代方案。
- 迁移、删除、覆盖、生产操作等破坏性动作必须再次核对精确目标与回滚方式。
- 不读取、记录或输出与任务无关的密钥和敏感数据。
- 遵守选定架构风格的依赖方向和边界；若现状冲突，记录冲突并单独规划迁移，不在普通任务中暗中重构。

### TEST

测试是独立于实现的质量门槛。进入本阶段时将任务状态设为 `TESTING`；测试通过前不得进入评审或标记 `VERIFIED`。

按风险选择并实际运行相关检查：

1. 目标测试或复现步骤。
2. 单元/集成/端到端测试。
3. 静态检查、格式检查、类型检查。
4. 构建或打包。
5. 安全、迁移、性能或兼容性专项检查（适用时）。

`enterprise` 任务还应根据影响验证性能/容量、故障恢复、可观测性、接口契约、发布和回滚；不适用时在 `test.md` 写明原因。

项目命令（首次配置时填写）：

```text
格式化：{{FORMAT_COMMAND}}
静态检查：{{LINT_COMMAND}}
类型检查：{{TYPECHECK_COMMAND_OR_NA}}
单元测试：{{UNIT_TEST_COMMAND}}
集成测试：{{INTEGRATION_TEST_COMMAND_OR_NA}}
构建：{{BUILD_COMMAND}}
```

必须在 `test.md` 记录测试范围、验收标准覆盖、实际命令、结果、失败项、未运行项及原因和残余风险。禁止把“预计通过”描述成“已通过”。

测试失败时：

- 如需修改代码，将状态退回 `IMPLEMENTING`，修复后重新进入 `TESTING`。
- 重新运行受影响测试及必要回归测试，不能只验证最后一个失败点。
- 无法执行的必要测试必须说明阻塞原因、替代证据和风险；不能将 `test_status` 标记为 `passed`。
- 只有必要测试均通过且 `test_status: passed` 时，才能将状态更新为 `VERIFIED`。

### REVIEW

评审必须读取 `test.md`，从正确性、边界条件、并发/幂等、失败恢复、安全、性能、兼容性、可维护性、测试充分性和文档一致性审查变更。问题按严重度记录；关键问题解决前任务不能完成。

### DOCUMENT

按变化类型同步：

| 变化 | 必须更新 |
|---|---|
| 项目目标/范围 | `.ai/project.md` |
| 模块、依赖、数据或部署 | `.ai/architecture.md` |
| 业务规则、术语、流程、状态 | `.ai/business.md` |
| 长期架构/业务取舍 | `.ai/decisions.md` |
| 阶段、完成项、风险、下一步 | `.ai/progress.md` |
| 使用方式、接口或运维 | 对应 README/API/运行手册 |

若判断无需更新，必须在任务 `result.md` 中说明原因。

## 7. 完成定义（Definition of Done）

任务只有同时满足以下条件才能标记 `DONE`：

- 验收标准逐项满足。
- 修改范围与批准计划一致，或范围变化有记录。
- 必要测试、静态检查和构建已通过。
- 没有未处理的关键评审问题。
- 回归、安全、兼容和运维风险已有结论。
- 已满足 `.ai/profile.md` 对当前交付级别和架构风格的适用要求。
- 相关文档和 `.ai/progress.md` 已同步。
- `task.md`、`plan.md`、`result.md`、`test.md`、`review.md` 无必填占位符。
- 未完成项和已知限制已显式列出，没有被隐藏。

## 8. 输出约定

计划阶段先给结论和影响范围；全部阶段完成后汇报：

1. 完成了什么。
2. 关键设计选择。
3. 独立测试阶段执行的命令、覆盖范围及结果。
4. 评审结论。
5. 文档更新。
6. 剩余风险或未完成项。

保持准确、简洁、可核验。引用真实文件路径和命令，不伪造执行记录。
